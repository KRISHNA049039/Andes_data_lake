# Requirements Document

## Introduction

Andes Data Lake is a centralized, ACID-compliant data lake for accounting datasets. It enables the upstream Controllership Team to publish datasets, and the BI Team to discover and subscribe to those datasets. The system supports both batch-ingested and live-streamed data (e.g., from stock markets), with pipelines that are reliable, consistent, and idempotent. Validation is enforced on streamed datasets to ensure data quality.

## Glossary

- **Data_Lake**: The centralized storage system that holds all accounting datasets with ACID transaction guarantees.
- **Dataset**: A named, versioned collection of accounting records published into the Data_Lake.
- **Controllership_Team**: The upstream team responsible for publishing and managing datasets in the Data_Lake.
- **BI_Team**: The downstream business intelligence team that discovers datasets and requests subscriptions.
- **Catalog**: The metadata registry that stores dataset descriptions, schemas, ownership, and discoverability information.
- **Subscription**: A granted access relationship between a BI_Team member and a Dataset, approved by the Controllership_Team.
- **Data_Pipeline**: The ingestion process that moves data from source systems into the Data_Lake.
- **Stream_Validator**: The component that validates live-streamed records against a defined schema before they are committed to the Data_Lake.
- **Ingestion_Engine**: The component responsible for executing Data_Pipeline runs, ensuring idempotency and consistency.
- **RBAC_Module**: The component responsible for enforcing role-based access control policies across the Data_Lake system.
- **Role**: A named set of permissions assigned to a user or team, defining what actions the user or team can perform within the Data_Lake.
- **Administrator**: A privileged user responsible for managing roles, users, and system-wide configuration of the Data_Lake.
- **Ingestion_Validator**: The component that performs structural and format validation on data at the point of ingestion into the Data_Lake.
- **Schema_Validator**: The component that validates records against the registered dataset schema, ensuring field types, required fields, and constraints are met.
- **Business_Rule_Validator**: The component that enforces domain-specific business rules on records after schema validation, such as cross-field consistency and accounting constraints.
- **Log_Store**: The centralized, scalable storage system for all operational and audit logs generated by Data_Lake components. DynamoDB is the recommended backing store for operational logs given the distributed, high-volume nature of the system.
- **Concurrency_Manager**: The component responsible for coordinating distributed concurrency across Data_Lake nodes, including distributed locking, leader election, and conflict resolution.

## Requirements

### Requirement 1: Dataset Publishing

**User Story:** As a member of the Controllership_Team, I want to publish datasets into the Data_Lake, so that accounting data is centrally available for downstream consumers.

#### Acceptance Criteria

1. WHEN the Controllership_Team submits a dataset for publishing, THE Catalog SHALL register the dataset with its name, schema, owner, and description.
2. WHEN a dataset is published, THE Data_Lake SHALL store the dataset contents in a durable, versioned format.
3. IF the Controllership_Team submits a dataset with a name that already exists, THEN THE Data_Lake SHALL create a new version of the existing dataset rather than overwriting it.
4. IF the dataset payload fails schema validation during publishing, THEN THE Ingestion_Engine SHALL reject the submission and return a descriptive error message.

### Requirement 2: Dataset Discoverability

**User Story:** As a member of the BI_Team, I want to discover available datasets in the Data_Lake, so that I can identify relevant accounting data for analysis.

#### Acceptance Criteria

1. THE Catalog SHALL list all published datasets with their name, description, schema, owner, and publication date.
2. WHEN a BI_Team member searches the Catalog by keyword, THE Catalog SHALL return all datasets whose name or description matches the search term.
3. WHEN a BI_Team member selects a dataset in the Catalog, THE Catalog SHALL display the dataset schema, version history, and owner contact information.

### Requirement 3: Subscription Management

**User Story:** As a member of the BI_Team, I want to request a subscription to a dataset, so that I can gain approved access to accounting data.

#### Acceptance Criteria

1. WHEN a BI_Team member requests a subscription to a dataset, THE Catalog SHALL create a pending subscription request and notify the Controllership_Team.
2. WHEN the Controllership_Team approves a subscription request, THE Catalog SHALL grant the BI_Team member read access to the dataset.
3. WHEN the Controllership_Team rejects a subscription request, THE Catalog SHALL notify the requesting BI_Team member with the rejection reason.
4. THE Catalog SHALL maintain a record of all active and revoked subscriptions for each dataset.
5. WHEN the Controllership_Team revokes a subscription, THE Catalog SHALL remove the BI_Team member's read access and notify the BI_Team member.

### Requirement 4: Reliable and Idempotent Data Pipelines

**User Story:** As a data engineer, I want data pipelines to be reliable, consistent, and idempotent, so that repeated or failed runs do not corrupt the Data_Lake.

#### Acceptance Criteria

1. THE Ingestion_Engine SHALL assign a unique idempotency key to each pipeline run.
2. WHEN the Ingestion_Engine processes a pipeline run with an idempotency key that has already been successfully completed, THE Ingestion_Engine SHALL skip the duplicate run and return the result of the original run.
3. IF a pipeline run fails midway, THEN THE Ingestion_Engine SHALL roll back all partial writes so that the Data_Lake remains in a consistent state.
4. WHEN a pipeline run completes successfully, THE Ingestion_Engine SHALL atomically commit all records to the Data_Lake in a single transaction.
5. THE Ingestion_Engine SHALL log the start time, end time, record count, and status of each pipeline run.

### Requirement 5: Live Stream Ingestion and Validation

**User Story:** As a data engineer, I want live stock market data streams to be validated before ingestion, so that only correct and complete records enter the Data_Lake.

#### Acceptance Criteria

1. WHILE the Data_Pipeline is receiving a live data stream, THE Stream_Validator SHALL validate each record against the dataset's registered schema before committing the record.
2. IF a streamed record fails schema validation, THEN THE Stream_Validator SHALL route the record to a dead-letter queue and log the validation error.
3. WHILE the Data_Pipeline is receiving a live data stream, THE Ingestion_Engine SHALL maintain ordering of records by their source timestamp.
4. IF the live data stream connection is interrupted, THEN THE Ingestion_Engine SHALL resume ingestion from the last successfully committed record offset.
5. THE Stream_Validator SHALL process each streamed record within 500 milliseconds of receipt.

### Requirement 6: ACID Compliance

**User Story:** As a data engineer, I want the Data_Lake to provide ACID transaction guarantees, so that concurrent reads and writes do not produce inconsistent results.

#### Acceptance Criteria

1. THE Data_Lake SHALL ensure that all write operations are atomic: either all records in a transaction are committed, or none are.
2. THE Data_Lake SHALL enforce consistency by rejecting any transaction that violates the dataset schema constraints.
3. WHILE a write transaction is in progress, THE Data_Lake SHALL isolate uncommitted changes so that concurrent readers observe only committed data.
4. WHEN a transaction is committed, THE Data_Lake SHALL persist the data durably so that committed records survive system restarts.
5. WHEN two concurrent write transactions conflict on the same dataset partition, THE Data_Lake SHALL resolve the conflict using optimistic concurrency control and retry the failed transaction.

### Requirement 7: Security and Role-Based Access Control

**User Story:** As an Administrator, I want to enforce role-based access control across the Data_Lake, so that each team can only perform actions appropriate to their role.

#### Acceptance Criteria

1. THE RBAC_Module SHALL define three roles: Controllership_Team_Role, BI_Team_Role, and Administrator_Role.
2. WHEN a user is assigned the Controllership_Team_Role, THE RBAC_Module SHALL grant permissions to publish datasets, approve or reject subscription requests, and revoke subscriptions.
3. WHEN a user is assigned the BI_Team_Role, THE RBAC_Module SHALL grant permissions to search the Catalog, view dataset metadata, and request subscriptions.
4. WHEN a user is assigned the Administrator_Role, THE RBAC_Module SHALL grant permissions to create and delete roles, assign roles to users, and configure system-wide settings.
5. IF a user attempts an action not permitted by the user's assigned Role, THEN THE RBAC_Module SHALL deny the action and return a descriptive authorization error.
6. THE RBAC_Module SHALL log every access control decision, including the user identity, requested action, and outcome.
7. WHEN an Administrator assigns or revokes a Role for a user, THE RBAC_Module SHALL apply the change immediately and record the change in an audit log.

### Requirement 8: Multi-Layer Data Validation

**User Story:** As a data engineer, I want data to pass through three layers of validation before it is committed to the Data_Lake, so that only structurally sound, schema-compliant, and business-rule-compliant records are stored.

#### Acceptance Criteria

1. WHEN a record is submitted for ingestion, THE Ingestion_Validator SHALL perform ingestion-time validation by checking the record format, encoding, and required header fields before further processing.
2. IF a record fails ingestion-time validation, THEN THE Ingestion_Validator SHALL reject the record and return a descriptive error indicating the structural issue.
3. WHEN a record passes ingestion-time validation, THE Schema_Validator SHALL validate the record against the dataset's registered schema, verifying field types, required fields, and value constraints.
4. IF a record fails schema validation, THEN THE Schema_Validator SHALL reject the record and return a descriptive error indicating the schema violation.
5. WHEN a record passes schema validation, THE Business_Rule_Validator SHALL evaluate the record against the dataset's configured business rules, including cross-field consistency checks and accounting constraints.
6. IF a record fails business rule validation, THEN THE Business_Rule_Validator SHALL reject the record and return a descriptive error indicating the violated business rule.
7. WHEN a record passes all three validation layers, THE Ingestion_Engine SHALL commit the record to the Data_Lake.
8. THE Ingestion_Engine SHALL record the validation outcome of each layer for every processed record in a validation audit log.

### Requirement 9: Centralized Logging

**User Story:** As a data engineer, I want all system logs to be stored in a centralized, scalable logging store, so that I can query operational and audit logs across all Data_Lake components from a single location.

#### Acceptance Criteria

1. THE Log_Store SHALL serve as the single destination for all operational logs, audit logs, and pipeline execution logs generated by Data_Lake components.
2. WHEN any Data_Lake component produces a log entry, THE Log_Store SHALL persist the entry with a timestamp, source component name, severity level, and correlation identifier.
3. WHEN a user queries the Log_Store by time range, component name, or correlation identifier, THE Log_Store SHALL return matching log entries ordered by timestamp.
4. THE Log_Store SHALL scale horizontally to handle increasing log volume without degradation in write throughput.
5. IF the Log_Store is temporarily unreachable, THEN THE producing component SHALL buffer log entries locally and retry delivery until the entries are persisted.
6. THE Log_Store SHALL retain log entries for a configurable retention period, after which entries are archived or deleted according to the configured policy.

### Requirement 10: Distributed Concurrency Handling

**User Story:** As a data engineer, I want the Data_Lake to handle concurrency in a distributed environment, so that concurrent operations across nodes do not cause race conditions, data corruption, or duplicate processing.

#### Acceptance Criteria

1. WHEN multiple nodes attempt to execute the same pipeline run concurrently, THE Concurrency_Manager SHALL acquire a distributed lock so that only one node executes the run at a time.
2. WHEN a distributed lock holder fails to renew the lock within the configured lease timeout, THE Concurrency_Manager SHALL release the lock so that another node can acquire it.
3. THE Concurrency_Manager SHALL elect a single leader node for each Data_Pipeline to coordinate partition assignment and checkpoint management.
4. IF the current leader node becomes unresponsive, THEN THE Concurrency_Manager SHALL trigger a new leader election within the configured failover timeout.
5. WHEN two nodes submit concurrent writes to the same dataset partition, THE Concurrency_Manager SHALL detect the conflict and resolve it using the versioned optimistic concurrency control policy defined for the dataset.
6. WHEN a BI_Team member and the Controllership_Team modify the same Subscription record concurrently, THE Concurrency_Manager SHALL serialize the operations so that the final state reflects both changes without data loss.
7. THE Concurrency_Manager SHALL log every lock acquisition, lock release, leader election, and conflict resolution event to the Log_Store.
